# BixLink（得盛國際）進出料庫存管理系統 — 架構設計 Spec

日期：2026-07-13
狀態：待使用者確認

## 1. 背景與目標

得盛國際有限公司（品牌 BixLink）是一家電池/電芯與電源相關產品（充電器、AC Adapter、面板等）的國際貿易與輕度組裝公司。目前用一份 Excel（`得盛料況總表`，14 個分頁、主記錄表 `2026` 已累積 2013~2026 年共 7,661 筆交易）加上一份獨立的編碼規則 Excel（`專案命名及編碼原則`，20 個分頁）手工管理料號、庫存進出、電芯批次追蹤與試產/量產紀錄。

目標：把這套已經運作多年、邏輯嚴謹但高度依賴人工的 Excel 系統數位化，優先解決操作花時間、人力成本高的問題，同時保留現有的料號編碼邏輯與批次追蹤能力。**不是**要建一套工廠等級的 WMS/MES（那是網路上抓到的另一份架構說明書的範疇，規模與本公司現況不符，本次設計刻意不採用）。

公司規模：目前不確定，但先以小規模（單人到個位數使用者）設計，架構要能之後擴充，不需要現在就做多人權限的完整分級。

## 2. Phase 1 範圍

包含：
- 物料主檔與料號編碼引擎（15 個基礎物料大類的完整編碼模板）
- 庫存與批次追蹤（含得盛倉庫 + 前瑞代工廠等多據點）
- 專案與生產追蹤（試產/量產、目標 vs 實際、各據點出貨/留樣）
- 國際貿易單據與往來對象（PI/CI/提單、多幣別、供應商/客戶主檔）
- 使用者與權限（輕量角色）
- 報表（現有庫存、進出流水、成本彙總）
- 歷史 Excel 資料遷移（2013~2026 全部交易記錄）

明確排除（非目標，之後有需要再開新 spec）：
- 微服務、事件匯流排（Kafka/RabbitMQ）、ELK、藍綠部署等工廠等級基礎設施
- PDA/平板離線掃描與斷網同步
- Wave picking、cross-docking、put-to-wall 等大宗倉儲揀貨演算法
- 與 MES 的 BOM 倒扣/在製品盤點整合
- 即時匯率 API（先用人工輸入/單據當下鎖定匯率）
- 物流商 API 自動對接（DHL/FedEx 自動列印提單）
- 電芯照片比對庫、現場標籤自動列印（低使用率，先不做）

## 3. 技術棧

| 項目 | 選擇 | 原因 |
|---|---|---|
| 全端框架 | Next.js (App Router) + TypeScript | 使用者已熟悉（project-golem 用同一套），單一 repo 可先本機跑，之後直接部署雲端不用換技術 |
| ORM / DB | Prisma + SQLite（開發）→ PostgreSQL（之後上雲時零改動切換） | 穩定、遷移工具成熟、schema 即文件 |
| 認證 | 輕量 session-based auth（如 Lucia 或 NextAuth Credentials） | 使用者少，不需要 OAuth2 gateway |
| Excel 匯入 | `xlsx`（SheetJS）寫一次性遷移腳本 | 讀取現有 14+20 分頁資料 |
| 單據 PDF | `@react-pdf/renderer` 或 `pdf-lib` | 產生 PI/CI/提單 |
| 部署 | 先本機/單機開發，之後再決定雲端或內部伺服器 | 使用者尚未決定 |

## 4. 模組地圖

1. **物料主檔與編碼引擎** — 大類/小類查找表、15 種大類的料號位元模板、供應商代碼表、客戶地區代碼表、序號計數器、專案代號產生器
2. **庫存與批次追蹤（多據點）** — 得盛倉庫 + 前瑞代工廠（可擴充其他據點）間的異動記錄、批次/Date code 履歷、批次→成品料號分配表（取代現有 Excel 的寬欄位設計）、儲位主檔
3. **專案與生產追蹤** — 專案代號、試產/量產階段、目標數 vs 實際數、各據點出貨數/留樣數
4. **國際貿易單據與往來對象** — 供應商/客戶主檔（含地區、幣別、別名）、PI/CI/提單產生、多幣別、HS Code、危險品文件（UN38.3/MSDS）附件
5. **使用者與權限** — 輕量角色（admin/倉管/業務/財務）
6. **報表** — 現有庫存、進出流水、成本彙總儀表板

## 6. 料號 / 專案編碼引擎設計

現況有兩套獨立編碼系統，設計上要分開處理：

1. **料號編碼（Item code）**：15 個基礎物料大類（0電芯、1電子…9板子、0包材、A電池…F膠類）**各自有不同的位元模板**（大類位、小類位、專案代號片段、序號等長度都不同），部分大類（如 A電池）會把專案代號片段直接嵌入料號中。因此不能用單一公式產生，必須設計成「模板表」：每個大類一筆設定，定義每個位元區段是「固定值」「查找表(如供應商代碼)」「專案代號片段」還是「流水序號」，由使用者（開發者）先把 15 個大類的模板都建進系統，之後照使用者要求（一次做完 15 種）在 Phase 1 內完成。
2. **專案代號（Project code）**：獨立一套模板（大類字母 + 化學代碼 + 年份 + 串併數 + 容量 + 流水號 + 客戶地區號段），套用在「專案」而非「物料」上。

料號第 1 碼「大類」的正式規則（2026-07-13 經使用者確認，取代隱藏分頁的過時定義）：
**1=成品、2=半成品、3=零件、4=原物料、5=消耗品、6=商品（不做加工，單純買賣）**。
系統以此六值做下拉選單與驗證，超出範圍即拒絕產生料號。

兩者都做成可設定的規則表，而不是寫死在程式邏輯裡 — 現有規則已經跑了 10 幾年沒大改過，但把它當設定資料存，比寫死更容易在真的要調整時修改，不需要改程式碼。

## 7. 資料遷移（Excel → 新系統）

來源：`得盛料況總表` 全部 14 分頁（含隱藏的歷史年度分頁）、`專案命名及編碼原則` 的 15 個大類模板 + 類別架構表。

已知會遇到的真實資料品質問題，遷移時要處理，不能假設乾淨：
- **Type 欄位無控制詞彙**：同一物料被打成不同字串（如 `電阻-0603` 與帶尾端空白的 `電阻-0603 `、`Housing` vs `Housing `、`label` vs `Label`）。遷移時做 trim + 大小寫正規化，仍有殘留的話先用 legacy_text 欄位保留原文字，不強制自動歸類。
- **供應商/客戶名稱不一致**：如 `東京週波` / `東京周波`（打字錯誤）/ `Tokyo Shuha`（英文）是同一個客戶；`邦聖` / `邦聖螺絲五金有限公司` 是同一供應商簡稱/全名。這需要人工比對建立別名對照表，系統無法自動可靠判斷，遷移時列出待確認清單交給使用者確認。
- **儲位欄位混雜**：真實資料裡除了正規儲位代碼（如 `H-15`、`CE-2`），還有中文詞當儲位用（`桌`、`座`、`防潮箱`）、甚至資料輸入錯誤（`James, K`、`?`）。Location 主檔要有 legacy_text 欄位承接這些例外，不強制一次全部規範化。
- **stage（物料種）不是類別的固定屬性**：例如 `PCBA` 在不同交易裡分別記錄為半成品或原物料。遷移時逐筆保留原始值，不用類別去推導。
- 有個別列出現明顯輸入錯誤（如把訂單號碼列表貼進 Customer 欄位），遷移腳本要能標記出「無法辨識」的列，而不是靜默丟棄或錯誤匯入。

**例外處理隔離區（Quarantine Zone）— 遷移的硬性規則：**
遷移腳本對每一列只有兩種結果：(a) 成功匯入目標表，或 (b) 整列原文（含來源檔名/分頁/列號）存入 `MigrationQuarantine` 隔離表並記錄失敗原因。**不存在第三種「跳過」或「自動修正後匯入但不留痕跡」的路徑。** 系統要提供一個隔離區管理頁面，讓倉儲人員逐筆檢視失敗列的原始內容，手動修正後重新匯入，或明確標記「確認捨棄」（留下操作記錄）。遷移完成的驗收標準是：成功匯入筆數 + 隔離區筆數 = 來源總筆數，兩邊對得起來才算完成。

## 8. 開發優先順序（Phase 1 內部順序）

1. 物料主檔 + 類別/供應商/客戶地區查找表 + 15 種料號模板 + 專案代號模板（先把設定資料建好，其他模組都依賴它）— **已完成**
2. 庫存與批次追蹤 schema + 服務層（Partner、Site、Location、Batch、InventoryTransaction、BatchAllocation），用小規模測試資料以 TDD 驗證，尚不接入真實歷史資料
3. 歷史資料遷移腳本（把 7,661 筆交易 + 批次資料匯入第 2 步已驗證好的 schema，含資料清理標記與隔離區）
4. 專案與生產追蹤
5. 往來對象主檔 + 貿易單據（PI/CI/提單）+ 多幣別
6. 報表儀表板

（2026-07-13 修正：原本把「歷史資料遷移」排在「庫存與批次追蹤」schema 之前，但遷移的目的地資料表本來就屬於後者，順序有誤，已對調。）
