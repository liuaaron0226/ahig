# ADR-0005：Skill 目錄系統的資料來源與分類策略

- 狀態：已接受
- 日期：2026-07-31
- 情境：建立可瀏覽／可搜尋的 skill 目錄系統

## 問題

要做一個能「看到所有已安裝 skill」並「依項目搜尋出該類別所有 skill」的系統，必須先決定：清單從哪來、如何分類。

## 調查發現

磁碟掃描的結果與實際可用清單並不一致：

| 位置 | SKILL.md 數 | 說明 |
|---|---:|---|
| `~/.claude/skills/` | 132 | 個人與 marketplace 安裝的 skill |
| `~/.claude/plugins/cache/` | 44 | 已安裝 plugin 的實體 |
| `~/.claude/plugins/marketplaces/` | 141 | git clone 的商店倉庫（含未安裝項目） |

去重後磁碟上約 213 個不重複名稱，但：

- **`gws-*`、`recipe-*`、`persona-*` 完全不在磁碟上**（`skills/` 目錄中這三種前綴各為 0 個），它們由 skill-seeker MCP server 提供。純磁碟掃描會漏掉約 100 個實際可用的 skill。
- marketplaces 中有 42 個名稱從未進入 cache，屬「可安裝但未安裝」。
- 73 個名稱存在多份副本（`frontend-design` 有 5 份），因為 marketplaces（原始碼）與 cache（安裝實體）本就是不同角色，非冗餘。

分類依據的可靠度也不如預期：可掃描到的 213 個中，**139 個（65%）沒有可用的名稱前綴**，僅 `gsd-`(67)、`ponytail-`(5)、`codex-`(2) 能靠前綴可靠歸類。

## 決策

**收錄範圍**：只列實際可叫用的 skill。marketplaces 中未安裝者不進主清單。

**資料來源**：三方合併——
1. 磁碟掃描 `~/.claude/skills/` 與 `~/.claude/plugins/cache/`，解析 frontmatter 取得 `name` 與 `description`
2. MCP 來源（`gws-*` / `recipe-*` / `persona-*` 等）以可維護的清單補入，標記來源為 MCP
3. 合併去重，每筆保留來源標記

**分類**：自動分類與全文搜尋並行。分類依證據強度排序——
1. 名稱前綴（事實，非推測）
2. description 關鍵字比對
3. 兩者皆無法判定者標為「未分類」，**不硬塞**

## 理由

- 使用情境是「我要做某件事，有哪些 skill 可用」。混入叫不出來的項目會讓每次搜尋都需要二次判斷。
- 硬把 skill 塞進固定類別會造成搜尋失效（分類錯 = 永遠搜不到）。標記「未分類」讓錯誤可見且可修。
- 全文搜尋涵蓋 name、description、category，因此即使分類判斷失準，搜尋仍是救援路徑。

## 後果

- MCP 來源的描述需一次性建立，日後新增需手動維護。該批以 Google Workspace 相關為主，變動不頻繁。
- 現有 `skills-reference.html` 為手寫靜態頁（最後更新 2026-07-12，分 11 類），已過時且每次新增都要手改。新系統以掃描器產生資料，取代手動維護。
- 「未分類」數量是分類規則品質的指標，應隨規則調整而下降。

## 已考慮但未採用

- **純磁碟掃描**：漏掉約 100 個 MCP 來源 skill。
- **純搜尋不分類**：使用者需求明確包含「跑出該類別所有 skill」。
- **收錄 marketplaces 未安裝項**：與「已安裝清單」是不同用途，混在同一介面會降低可信度。
