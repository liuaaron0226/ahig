# W4b 設計輸入

**依協調者裁定 n+77 建立（第 371 輪，2026-08-18）。**

## 這份檔案的規則

n+42 原訂「終止後彙整」，n+77 判定該指令有缺陷：終止後才彙整，做法必然是
回頭讀 111 個看板區塊的敘述再整理成交付物，**那正是第九型缺陷（以自己產生的
敘述作為資料來源）**，而且是在最大規模上、沒有第二次機會、交給擁有者的東西上。

故改為：

1. **識別當輪即寫入**，不事後重建。
2. **每條至少含：類別／`candidateId`／一句主張／來源輪次。**
   **🚨 `candidateId` 是重點——條目要能回溯到記錄，而不是回溯到我們的敘述。**
3. **回填分批進行**，每輪一小批，讓每批都能被下一輪檢查。
4. **回填時逐項回到 `candidateId` 讀判讀原文，不得只讀看板敘述。**
5. **找不到對應 `candidateId` 者，如實標記為「僅存敘述、無法回溯」**
   ——那本身就是要交給擁有者的資訊。

## 兩個來源的規模（實測，`.scratch/n77_w4b_seed.py`）

```
甲 判讀理由提及 W4b        808 筆  ← 可回溯至 candidateId
乙 看板「W4b 設計輸入」區塊 111 次  ← 協調者所指之 111
```

**🚨 兩者不是同一個集合，也不是包含關係。**
甲是「判讀時寫下建議 W4b 如何使用本筆」者；乙是「心跳中整理成區塊」者，
**一個區塊常涵蓋數筆或零筆記錄**。
**⚠️ 回填以甲為準（有 candidateId），乙僅用來找出「僅存敘述」者。**

**⚠️ 甲的 808 筆遠多於協調者所見的 111**——這代表回填工作量比裁定當時所估為大，
但也代表可回溯的比例比預期高。分批進行時每批以頁段切分。
